# 同步协议 v1

> 服务端实现：`server/main.go`；Windows 端：`windows/main.go`；Android 端：`Protocol.kt` + `SyncEngine.kt`
> **改协议必须三处同步修改**，否则跨端会静默失效（未知类型被忽略，不会报错，只会"没反应"）。

## 1. 传输层

| 项 | 值 | 代码位置 |
|----|-----|----------|
| 地址 | `ws://<host>:<port>/ws` | `server/main.go` `main()` |
| 帧类型 | 文本帧，UTF-8 JSON | — |
| 单条消息上限 | 8 KB（超出直接断开） | `conn.SetReadLimit(8 * 1024)` |
| 服务端 PING | 每 20s 一次 | `PING_PERIOD` |
| 读超时 | 60s（收到 PONG 重置） | `PONG_TIMEOUT` |
| 限流 | 每连接 40 条/秒，超出返回 `error` | `RATE_LIMIT` |
| 健康检查 | `GET /health` → `{"status":"ok","rooms":N}` | — |

v1 使用明文 `ws://`，因此**不需要域名和备案**（纯 IP 直连）。若日后加 TLS，两端都换成 `wss://` 即可，协议本身不变。

## 2. 消息通用结构

所有消息共用一个扁平结构，按 `type` 区分，未用字段可省略（`omitempty`）：

```json
{
  "type": "play",
  "room": "7M8QW6",
  "name": "小明",
  "position": 123.4,
  "rate": 1.0,
  "state": "playing",
  "operator": "小明",
  "anchorMs": 1730780000123,
  "members": [],
  "error": "",
  "file": "movie.mkv",
  "size": 1234567890,
  "duration": 7200.5
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | 消息类型，必填 |
| `room` | string | 房间码，6 位大写字母+数字（去掉易混字符 `I/O/0/1`） |
| `name` | string | 昵称，房间内唯一 |
| `password` | string | 房间密码（可选） |
| `position` | float | 播放进度，单位**秒** |
| `anchorMs` | int64 | 锚点的服务器时间戳，**毫秒** |
| `rate` | float | 倍速，默认 1.0 |
| `state` | string | `playing` / `paused` / `buffering` |
| `operator` | string | 触发本次变更的昵称（用于"谁操作的"提示） |
| `members` | array | 成员列表，见下 |
| `error` | string | 错误描述 |
| `file` / `size` / `duration` | string/int64/float | 片源信息，用于一致性提示 |

`members` 元素：

```json
{ "name": "小明", "state": "playing", "file": "movie.mkv", "duration": 7200.5, "online": true }
```

## 3. 消息总表

### 客户端 → 服务端

| type | 载荷 | 说明 |
|------|------|------|
| `join` | `room`(空=建房), `name`, `password` | **必须是首条消息**，否则返回 `error: join first` |
| `play` | `position`, `rate?` | 请求播放（含倍速变更） |
| `pause` | `position` | 请求暂停 |
| `seek` | `position` | 请求跳转 |
| `heartbeat` | `position`, `rate` | 每 5s 一次，用于漂移检测 |
| `memberState` | `state` | 上报自己的播放器状态（加载/缓冲时用） |
| `fileInfo` | `file`, `size`, `duration` | 进房后上报片源信息 |
| `leave` | — | 预留（v1 直接断开连接即可） |
| `chat` | — | 预留，服务端目前忽略 |

### 服务端 → 客户端

| type | 载荷 | 说明 |
|------|------|------|
| `hello` | `room`, `state`, `position`, `anchorMs`, `rate`, `members` | 加入成功后的全量状态，客户端据此定位 |
| `sync` | `state`, `position`, `anchorMs`, `rate`, `operator` | 状态变更广播。**不回显给发起者**（发起者本地已执行） |
| `forceSeek` | `position`, `operator` | 漂移超阈值时的强制纠偏，`operator` 固定为 `server(drift)` |
| `members` | `members` | 成员列表变化（进/出/状态变更/片源上报） |
| `join` | `name` | 有人加入（客户端提示"X 加入了房间"） |
| `leave` | `name` | 有人离开 |
| `joinError` | `error` | 加入失败（房间满/密码错/重名/缺昵称），**服务端随后断开连接** |
| `error` | `error` | 非致命错误（限流、JSON 解析失败、未 join） |

## 4. 加入流程

```
客户端                          服务端
  │  ── join{name,room?,pwd} ──►  │  房间不存在则创建；校验密码/人数/重名
  │  ◄──── hello{全量状态} ─────  │  同时向房间其他人广播 join + members
  │  ── fileInfo ──────────────►  │
  │  ◄──── members ────────────   │
  │  ── memberState ───────────►  │
  │  ── heartbeat (每 5s) ─────►  │
```

客户端收到 `hello` 前**不要**上报本地播放事件（mpv 启动瞬间的初始暂停会误广播，打断别人的播放——这是 v0.1 修过的真实 bug）。

## 5. 房间状态机

服务端只保存**一个**房间级状态，成员操作直接改写它：

```
        play(position)
  paused ─────────────► playing
    ▲                     │
    └─────────────────────┘
       pause(position)
```

- 任一成员 `play` → `state=playing`，`position=该成员上报值`，`anchor=now`
- 任一成员 `pause` → `state=paused`，`position=该成员上报值`
- 任一成员 `seek` → 只改 `position/anchor`，**不改变 `state`**
- 权威进度：`currentPos() = state==playing ? position + (now-anchor)*rate : position`

因此"最后操作者胜出"，不存在两端各自为政的竞态。

## 6. 防抖与纠偏

### seek 防抖（服务端）

首次 seek 启动 120ms 定时器，窗口内的后续 seek 只更新 `position` 不重置定时器；定时器到点广播**最后一次**的位置。效果：拖动进度条只产生一次广播，且落在终点。

### 漂移检测（服务端）

```
expected = currentPos()
drift    = 客户端心跳 position - expected
|drift| > 1.0s  → 广播 forceSeek(当前权威位置)
```

仅当房间处于 `playing` 时才检测（暂停时客户端进度就是权威值）。阈值见 `DRIFT_SOFT=0.3` / `DRIFT_HARD=1.0`。

### 客户端自纠（无广播）

客户端比对心跳回执与本地进度，|偏差| 在 0.3~1.0s 之间时**静默 seek**（不弹提示、不上报），避免频繁纠偏造成可见跳动。

## 7. 房间生命周期

| 事件 | 行为 |
|------|------|
| 建房 | `join` 时 `room` 为空 → 服务器生成 6 位房间码返回 |
| 空房 | 最后一人断开 → 立即从内存删除 |
| 过期 | 后台每 5 分钟清理"空且创建超 2 小时"的房间（兜底） |
| 重启 | 所有房间丢失，客户端重连时会用原 `room` 码重新 `join`，但房间码已失效 → 需重新建房 |

v1 不做持久化，符合"看完就散"的使用场景。

## 8. 错误信息

| error 文本 | 触发条件 | 客户端处理 |
|------------|----------|-----------|
| `name required` | join 未带昵称 | 提示用户填昵称 |
| `wrong room password` | 密码不符 | 提示重新输入 |
| `room full (max 5)` | 房间已满 | 提示房间满 |
| `name already taken in room` | 昵称重复 | 提示换昵称 |
| `join first` | 首条消息不是 join | 客户端 bug |
| `rate limit exceeded` | 超 40 条/秒 | 忽略/退避 |
| `bad json` | 解析失败 | 客户端 bug |

## 9. 如何扩展协议

以"新增 `speed`（倍速）独立消息"为例，需要改三处：

1. **服务端** `server/main.go`
   - `Msg` 结构体加字段（若已有 `rate` 可复用则不必加）
   - `readLoop()` 的 `switch msg.Type` 加 case，改房间状态后调用 `broadcastSyncLocked(m)`
2. **Windows** `windows/main.go`
   - `Msg` 结构体加字段
   - `wsReadLoop` 的 switch 加对 `sync` 的处理（已有 `rate` 字段则只需让 mpv 执行 `speed` 命令）
3. **Android** `Protocol.kt` / `SyncEngine.kt`
   - `SyncEngine` 的 `when (type)` 加分支，调用 `player.setSpeed()`

兼容性原则：

- 新增字段用**可选**（客户端缺省即用默认值），老客户端不会崩；
- 新增消息类型时，老客户端会忽略未知 type —— 所以**不要**把关键行为塞进新类型而不给降级路径；
- 不要修改已有字段的含义，宁可加新字段。

**回归测试**：改完用 `tools/sim`（模拟两个成员）+ `tools/ctl`（发单条指令）验证，无需开播放器：

```bash
cd tools/sim && go run . -room TEST01     # 端 A，自动应答
cd tools/ctl && go run . -room TEST01 -name b -cmd play -pos 100
```
