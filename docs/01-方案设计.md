# 「一起看」方案设计（需求 · 架构 · 风险）

> 版本：v0.2（2026-11-05，已随 v0.1 实现同步更新）
> 范围：2~5 人异地同步观看各自本地已有的视频文件，播放/暂停/进度全同步，Windows + Android 双端，架构上规避 PCDN 风险。

| 阶段 4 | 部署运维（Docker Compose、加固、监控） | 🟡 Docker 化与开机自启已完成，监控待做 |

与初稿的偏差（实现时做的取舍）：

1. Windows 客户端形态从"托盘程序"简化为**控制台窗口**（功能一致，省掉 GUI 框架依赖，v0.1 以可用为先）；
2. Android 未引入 ffmpeg 解码扩展，依赖系统解码器（H.264/H.265+AAC 全覆盖，DTS 等特殊音轨不支持）；
3. Android 未做前台 Service，改为**亮屏播放**（观影场景本身要看屏幕，先省掉常驻通知的复杂度）；
4. 服务端增加 `memberState` 消息与操作者归因，落地了 R7 成员状态需求。

## 一、需求分析

### 1.1 核心需求

| 编号 | 需求 | 说明 |
|------|------|------|
| R1 | 多人房间 | 2~5 人进入同一"房间"，观看同一部影片 |
| R2 | 本地片源 | 每位观看者设备上已有同一视频文件，**无需传输视频数据** |
| R3 | 播放同步 | 任一人播放/暂停/拖动进度/调节倍速，其他人跟随 |
| R4 | 双端客户端 | Windows 客户端 + Android 客户端 |
| R5 | 中心服务器 | 阿里云 ECS（Alibaba Cloud Linux）作为同步服务器 |
| R6 | 规避 PCDN 风险 | 架构上杜绝"家庭宽带上行大流量视频分发"的形态 |
| R7 | 成员状态提示 | 可视化展示"谁暂停了/谁在缓冲/谁掉线了"，操作可归因 |
| R8 | Android 分发方式 | 仅 APK 侧载分发（官网/直链下载），不上架应用市场 |

### 1.2 明确不做（本期范围外）

- ❌ 视频流分发 / 转码 / 在线片库（流量模型完全不同，若做则作为二期单独评估）
- ❌ 客户端之间 P2P 传输（这正是 PCDN 风险的主要来源，明确禁止）
- ❌ 语音/文字聊天（协议里已预留 `chat` 类型，可后续加，技术上很轻）
- ❌ 弹幕（v1.1 增量，纯信令即可实现）

## 二、PCDN 风险分析与规避（本方案的立足点）

### 2.1 什么是 PCDN 风险

运营商对家庭宽带持续检测：若**上行**出现大流量、长持续、多连接的视频流特征（典型的 P2P/PCDN 分发模式），可能被判定为"经营性带宽/PCDN"，后果包括限速、封停宽带、要求说明用途。近两年运营商对此打击很严。

### 2.2 本方案的流量模型为什么天然安全

```
观看者A ──┐                          ┌── 观看者B
          │   仅同步指令（< 2 KB/s）    │
          ├──► 云端房间服务器 ──────────┤
          │   play/pause/seek/心跳     │
观看者C ──┘                          └── 观看者D
```

- 视频文件在每个人本地磁盘上，**视频数据零传输**
- 网络上流动的只有信令：播放状态、进度、心跳，每条消息几十到几百字节
- 单房间总带宽 < 10 KB/s，即使全天运行，月流量也不过几百 MB
- 所有流量经由云主机（机房带宽，本身就是合法商业带宽），家庭宽带上行无任何视频特征

**结论：只要坚持"信令走云端、片源各自本地、不做客户端互传"三原则，PCDN 风险趋近于零。**

### 2.3 红线（写进设计约束，改代码时不要越过）

1. 任何时候不得引入客户端间直接传输视频数据的机制（哪怕"只是缓存共享"）；
2. 若二期要支持"一人有片源分发"，必须走服务器中转并单独评估带宽费用，且观看者侧只有下行（下行大流量不触发 PCDN 判定，风险在上行——但仍建议保持克制）；
3. 服务器不做公开文件服务，防止被扫描者滥用为图床/代理（这会带来真实的风控与法律风险）。

## 三、总体架构

### 3.1 组件职责

```
┌─────────────────────────────────────────────────┐
│                云端主机（最低配即可）                │
│  ┌───────────────────────────────────────────┐  │
│  │  同步服务器（WebSocket 房间服务）             │  │
│  │  · 房间管理（创建/加入/退出/成员广播）         │  │
│  │  · 播放状态机（权威房间状态）                 │  │
│  │  · 指令中转与防抖                           │  │
│  │  · 简单鉴权（房间码 + 房间密码）              │  │
│  └───────────────────────────────────────────┘  │
│  部署形态：Docker 容器（restart=unless-stopped）   │
└───────────────▲─────────────────▲───────────────┘
        ws:// 信令          ws:// 信令
    ┌───────────┴────┐  ┌────┴───────────┐
    │ Windows 客户端  │  │ Android 客户端  │
    │ 播放内核: mpv   │  │ 播放内核:       │
    │ 通信: WebSocket │  │  Media3/       │
    │                │  │  ExoPlayer     │
    └────────────────┘  └────────────────┘
        本地文件              本地文件
```

服务端**不接触任何视频数据、不落盘任何状态**（房间存在内存里），因此可以随时重启与迁移。

### 3.2 技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 服务端 | **Go** | 单二进制部署极简、内存几 MB、goroutine 模型很适合房间广播 |
| 通信协议 | **WebSocket + JSON** | 双端生态成熟（OkHttp / gorilla），消息量小无需二进制协议；后期需要再换 MessagePack |
| Windows 播放内核 | **mpv（JSON IPC 控制）** | ffmpeg 系全格式支持，无需自己写播放器 |
| Windows 客户端 | **Go 控制台程序 + mpv** | 与 mpv 的命名管道通信简单可靠，交叉编译单文件 |
| Android | **Kotlin + Media3 ExoPlayer + OkHttp** | 官方播放器，依赖体积可控，minSdk 24 覆盖绝大多数设备 |
| 部署 | **Docker + compose** | 一条命令起停，升级/迁移都是分钟级 |

### 3.3 备选方案对比（为什么不用现成的）

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| 开源 Syncplay | 成熟稳定，Windows 客户端开箱即用 | **无官方 Android 客户端**，专用 TCP 协议，移动端集成成本不低于自研 | 可用于快速体验验证，但不作为最终产品 |
| Web 端（浏览器 video） | 跨平台免安装 | 浏览器解码格式差（HEVC/DTS/外挂字幕全灭），本地文件访问受限 | 仅作未来轻量补充 |
| 自研（本方案） | 协议可控、双端一致、可长期演进 | 有开发量 | **采用** |

## 四、同步协议设计（摘要）

完整字段、时序、扩展方法见 [02-同步协议.md](02-同步协议.md)。

### 4.1 房间权威状态

服务器为每个房间维护一份权威状态，任意成员操作后立即广播：

```json
{
  "state": "playing",
  "position": 1234.5,
  "anchorMs": 1730780000123,
  "rate": 1.0
}
```

- `position` 是锚点时刻的进度（秒），`anchorMs` 是锚点的服务器时间（毫秒）
- 客户端推算当前进度：`position + (now - anchorMs)/1000 × rate`

### 4.2 防漂移算法

1. **心跳比对**：客户端每 5 秒上报本地进度；
2. **阈值**：偏差 < 300ms 忽略；300ms ~ 1s 客户端静默微调；> 1s 服务器广播 `forceSeek` 强制纠偏；
3. **暂停语义**：暂停以"最后一次操作"为准，服务端记录精确 position，杜绝"你暂停了但我还在放"的竞态；
4. **指令防抖**：seek 连发时服务器合并（120ms 窗口只广播最后一次），避免画面疯狂跳动。

### 4.3 片源一致性校验

进房时上报文件名、大小、时长。时长不一致即提示"片源版本可能不同"（导演剪辑版 vs 公映版是异地同步最常见的翻车原因）。同内容不同封装（MKV vs MP4）只要时长一致即可正常同步。

## 七、风险清单与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| 片源版本不一致导致"越看越歪" | 高 | 进房上报时长并展示；心跳纠偏兜底 |
| 暂停/播放竞态（两人同时操作） | 中 | 服务端权威状态机 + 最后操作者胜出 + 广播合并 |
| Android 厂商杀后台导致掉线 | 中 | 亮屏播放 + 断线自动重连（30 次 × 5s），重连后拉全量状态追赶 |
| 弱网下指令延迟感知明显 | 中 | 信令极小，正常网络 < 100ms；本地立即执行 + 服务器确认 |
| 服务器被扫描滥用 | 低 | 房间密码 + 人数上限 5 + 每秒 40 条限流 + 单一端口 |
| PCDN 误判 | 极低 | 家宽侧无上行视频流量；不做 P2P 分发 |
| 主机到期/迁移 | 低 | 容器化 + 无状态，10 分钟迁移 |
